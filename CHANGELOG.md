- Detectado que no había ningún backup a nivel de base de datos (solo el Auto Backup de VM de Contabo, no verificable desde el VPS). Agregado `scripts/backup_postgres.sh` (pg_dump + gzip) programado por cron del usuario `fernando` a diario a las 03:00, con 14 días de retención — ver ADR-004.

Probado forzando cada caso. Ver ADR-004.

## 2026-08-03

- Agregado ADR-021: servicio real `orchestrator` en `docker-compose.yml` — cableado mínimo, sin lógica de negocio ni disparador automático (el proceso principal es `sleep infinity`, se invoca a mano). Cierra el pendiente de Fase 3 de ADR-016 (autenticación por suscripción verificada desde un servicio real, no un contenedor descartable) y la condición de ADR-017 (ya no vacía: hay una tool MCP real corriendo). Usa `claude-agent-sdk==0.2.89` (pin exacto, verificado contra el tag real del repo oficial; se evaluó y descartó la última, `0.2.128`, mismo criterio conservador de ADR-020), conectado por subproceso stdio a `mcp_servers/django_project` (ADR-020). `tools=[]` deshabilita todas las tools built-in de Claude Code como política de seguridad (ADR-015) en vez de una lista negra frágil. UID del contenedor parametrizado vía `ORCHESTRATOR_UID` (nunca cableado), montaje del credencial y del repo ambos en solo lectura.
- Durante la verificación end-to-end de ADR-021 se encontraron y corrigieron dos problemas reales antes de dar el servicio por bueno: (1) sin `strict_mcp_config=True`, el SDK cargaba además conectores de la cuenta real asociada al credencial (apareció "claude.ai Google Drive", nunca configurado por este proyecto) — corregido agregando ese flag; (2) `query()` de una sola pasada respondía en el primer turno con el MCP todavía en estado `pending`, así que el modelo contestaba como si la tool no existiera — corregido reemplazando por `ClaudeSDKClient` con polling explícito y determinista de `get_mcp_status()` antes de mandar el prompt. Verificado después con tres prompts reales (PONG puro, `git_status`, `read_file`): los tres respondieron correctamente, incluyendo el estado real del repo. Queda documentado como hallazgo residual no resuelto que, aun con `tools=[]`, cuatro tools (`DesignSync`, `Monitor`, `PushNotification`, `RemoteTrigger`) siguen apareciendo disponibles — ninguna da acceso a filesystem/shell, no bloqueante para esta entrega. Actualizados ARQUITECTURA.md §2/§6, `docs/DEPENDENCIAS.md`, y enmendadas ADR-016/ADR-017 marcando sus pendientes de Fase 3 como resueltos.
- En revisión de ADR-021, encontrado que el mount del credencial dependía de `${HOME}` del usuario que corre `docker compose`, no de una variable propia del proyecto — corregido a `ORCHESTRATOR_CREDENTIALS_PATH`, mismo patrón que `ORCHESTRATOR_UID`, ambas documentadas en `env.example`. Reverificados los tres tests end-to-end con el nombre nuevo.
- Enmendada ADR-011 (hallazgo de la misma revisión): verificado en vivo que el cache-busting con `?v=<único>` ya no es confiable — tres pedidos consecutivos a `raw.githubusercontent.com`, cada uno con un parámetro distinto, devolvieron el mismo contenido desactualizado (`x-cache: HIT`, `source-age` creciente). El CDN de GitHub está ignorando el query string para su cache key en esta ruta, al menos en esta fecha, y puede fallar en silencio sin ningún indicio. Reemplazado (no complementado) por un protocolo de dos pasos: pedir primero `api.github.com/repos/racetech-22/ia-central/commits/<rama>` para obtener el SHA real del HEAD, y después pedir cada archivo anclado a ese SHA exacto (`raw.githubusercontent.com/racetech-22/ia-central/<SHA>/<path>`), nunca al nombre de la rama — el contenido de un SHA fijo es inmutable, no hace falta cache-busting contra él. Actualizada la sección "Fuente de verdad en vivo desde GitHub" de CLAUDE.md con el mismo protocolo.
- Enmendada ADR-021: investigadas las 4 tools residuales que quedaban disponibles pese a `tools=[]` (`DesignSync`, `Monitor`, `PushNotification`, `RemoteTrigger`) — la afirmación anterior de que "ninguna da acceso a filesystem ni shell" era una suposición no verificada, y resultó ser falsa para al menos una. Confirmado contra la documentación oficial de Claude Code: `DesignSync` tiene efecto real, no es inerte — puede leer archivos del filesystem local (dentro del `localDir` de un plan) y subirlos (`write_files`) a un proyecto externo en `claude.ai/design`, sin pasar por `security.py` ni por ninguna tool MCP de este proyecto. `RemoteTrigger` podría programar disparadores propios en la nube (contradice "sin disparador automático" de ADR-021) y `PushNotification` saca texto arbitrario del contenedor vía infraestructura de Anthropic. Verificado (dos corridas limpias) que `disallowed_tools=["DesignSync","Monitor","PushNotification","RemoteTrigger"]` sí las saca del `SystemMessage`, a diferencia de `tools=[]` solo — pero no se aplicó como fix: al haber al menos una tool con efecto real, la decisión de qué mitigación adoptar (y si esta lista de cuatro es exhaustiva) queda para Fernando, no aplicada unilateralmente. Criterio operativo de tres partes: un límite que protege del operador se descarta (no hay segundo usuario ni tercero hostil, ADR-006 ya fijó que la defensa real es el acceso SSH restringido, no roles ni permisos por usuario); un límite que protege de una equivocación irreversible o de un agente descontrolado se conserva y se refuerza (nombra explícitamente el hook de ADR-007, el fail-closed de ADR-025 §9.4, y el aislamiento de proceso del Ejecutor de ADR-028); un límite de recurso no es un límite de política y se resuelve ampliando el recurso, no rediseñando alrededor (el techo de 2-3 Ejecutores simultáneos de ADR-030, que sale de la RAM del VPS, no de una decisión de seguridad). Declarado explícitamente que este principio no relaja ninguna de las tres decisiones que nombra — las tres caen del lado que se conserva — y que invocarlo para levantar alguna de ellas sería un uso incorrecto. Corregido de paso en el mismo cambio: ARQUITECTURA.md §1 decía "tres condiciones simultáneas" antes de agregar el cuarto punto — pasa a "cuatro", coherencia interna del propio documento. `docs/estado.yml` deliberadamente sin tocar: esta ADR no agrega ni cierra piezas ni decisiones abiertas, es un principio, no una pieza del mapa.
